## Root causes found

### 1. Automation was disabled

`automation.bathroom_heating_rack_v1_0_0` had `state=off` since **2026-04-20T17:01:11 UTC (Mon 19:01 CEST)** — nearly 48 hours. The user didn't remember turning it off; most likely an accidental click on the enable toggle in the HA UI while they were editing input overrides on Monday (that save added `boost_target_temp: 26`, `boost_runtime_min: 55`, `warmup_min_minutes: 28`, per-day evening days, etc.). At 17:00:55 there's a `user_id`-tagged state change on the automation entity in the logbook, immediately before a burst of boost/vacation toggles at 17:01–17:03 — classic "nothing's working, let me tap harder" frustration pattern.

**Impact:** no Morning A heating on Tue 2026-04-21 or Wed 2026-04-22. No notifications of any kind. No response to boost/vacation toggles. "Hit or miss" = worked Sun night and Mon up to 17:01, then silent.

**Fix:** turned it back on via `automation.turn_on` service call. Verified `state=on`, `last_triggered` updating on the next minute-tick.

### 2. Dashboard boost button works — but v1.1.0 fan-coord masks it

The `input_boolean.heating_rack_boost` had not changed state for 2,100 minutes (35 hours) before my test — which at first looked like the dashboard button was dead. Turned out that was just consistent with the automation being off; once the automation was on, the user tapped the button and the state transitioned to `on` correctly.

But the symptom the user reported — "boost does nothing" — was still valid, because of the v1.1.0 priority waterfall:

```
P1 vacation > P2 fan_coord > P3 boost > P4 evening > P5 morning > P6 idle
```

When the fan was on AND boost was on, `P2 fan_coord` won and demoted boost to `setpoint=idle_setpoint (7°C)`. The user's shower at 07:05 left the fan running (humidity-driven from the `bathroom_ventilator` automation), and tapping boost at 09:29 silently went nowhere visible. The fan-coord rationale from the v1.0.x spec was "don't heat air that's being evicted during showers" — a reasonable automatic optimization, but it violated the user's explicit-intent expectation when they tapped boost.

**Fix (v1.1.1):** reorder the priority waterfall so boost beats fan_coord:

```
P1 vacation > P3 boost > P2 fan_coord(morning/evening only) > P4 evening > P5 morning > P6 idle
```

Implementation: three single-line Jinja templates in the `- variables:` block at `bathroom_heating_rack.yaml:565` (desired_preset), `572` (desired_setpoint), `573` (active_priority). Commit `9881a51`. Labels `P2_fan_coord` and `P3_boost` kept for backward-compat with the notification condition checks that literal-match on them (e.g., `active_priority in ['P3_boost','P4_evening','P5_morning']`). A comment above the variables block documents that the numeric suffix is now historical.

## Known behaviors / follow-ups

### HA restart gotcha

Twice in one week a full `homeassistant.restart` left the `automation.bathroom_heating_rack_v1_0_0` entity missing from the state registry for 40+ seconds while the config was already loaded. Both times, running `hass-cli service call automation.reload` immediately instantiated it. First observed 2026-04-19 after the v1.1.0 reimport; repeated 2026-04-22 after the v1.1.1 reimport. Likely a race between config_entry load and automation entity platform setup when blueprint-based automations are in play.

**Workaround:** after every HA restart, if the heating-rack automation doesn't show up within 30s, call `automation.reload`. No data loss either time.

### Scheduled P4/P5 routines still fan-pause

By design: auto-scheduled Morning A/B and Evening A/B routines still get demoted to `P2 fan_coord` when the fan is on, because they don't represent explicit user intent. Only the user-tapped `input_boolean.heating_rack_boost` beats fan-coord in v1.1.1.

### Fan is still running 3+ hours after morning shower

At 09:48 the fan had been on since 07:05 (2h43m) because `bathroom_ventilator_v1_0_0` keeps it running while humidity is elevated. Not in scope of this session but worth watching — if humidity recovers slowly in the bathroom, the fan may stay on long past when a user would want to heat the room.

### Tuya beep-mute — still open

The LocalTuya investigation (from 2026-04-19 wrap) has not started. Still the next workstream after this session. Current beep count per transition is low (the idempotent-skip pattern keeps it to ~2 beeps per routine-transition cycle), so not blocking.
